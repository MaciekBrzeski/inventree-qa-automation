# INV-PARTS-003 — POST /api/part/ accepts payloads without `category`

## Summary

The OpenAPI schema for `POST /api/part/` marks `category` as part of the `Part` request schema, and the InvenTree UI "Create Part" form presents the Category picker prominently. A reasonable reading — and the one our generated manual test case `API-PARTS-053` initially made — is that `category` is required: POSTing without it should return `400`.

In reality, `POST /api/part/` with **only** `{"name": "..."}` returns `201 Created` with `category: null`. The part is saved as uncategorised. This is either an under-documented intended behaviour or a missing validation.

## Environment

- InvenTree: version `1.3.0`, apiVersion `477`.
- Endpoint: `POST /api/part/`.
- Auth: Token auth, admin user.

## Steps to reproduce

```http
POST /api/part/
Authorization: Token inv-<admin-token>
Content-Type: application/json

{"name": "category-less-probe"}
```

**Expected** (per the UX and our reading of the schema): `400 Bad Request` with a DRF validation error on `category`.

**Actual**: `201 Created`. Response body (abridged):

```json
{
  "pk": 11,
  "name": "category-less-probe",
  "IPN": "",
  "description": "",
  "category": null,
  "category_detail": null,
  "category_path": null,
  "active": true,
  "assembly": false,
  "component": true,
  "purchaseable": true,
  "salable": false,
  ...
}
```

Note also the defaults: `active=true`, `component=true`, `purchaseable=true`, `IPN=""`.

## Impact

- **Severity: low.** No crash, no data loss. The part can be re-parented later via PATCH.
- **Consequence for QA automation**: any test suite that assumes `POST /api/part/` rejects a missing category will go green on the negative case when it should be red. Our Phase 2 `API-PARTS-053` test case was wrong on the first draft for exactly this reason — the case was generated by qa-gemma from the OpenAPI description, which did not capture the real loose behaviour.
- **Consequence for UX integrity**: the UI and the API disagree about what a "valid part" means. Users who script part creation and forget the category will end up with uncategorised parts that do not show under any category tree and are only findable via direct search.
- **Consequence for downstream integrations**: importers, ERP bridges, and sync jobs that currently send `category: null` (intentionally or by mistake) silently bypass a validation the authors probably intended.

## Proposed fixes (in order of preference)

1. **Best**: add an explicit `required=True` on the `category` field of the Part serializer. Preserves schema-first behaviour; surfaces misuses early.
2. **Alternative**: if uncategorised parts are a supported product decision (e.g. staging imports), document the behaviour in `docs.inventree.org/en/stable/part/` and add a dedicated "Uncategorised" bucket in the UI so users can find them. Also update the OpenAPI `PartCreate` schema to mark `category` as explicitly `nullable` and not in the `required` list.
3. **Workaround in consumers**: tests should assert the actual `201 + category: null` behaviour until upstream decides. `API-PARTS-053` in our suite has been rewritten accordingly.

## Workaround applied in this repo

`submission/automation/api/tests/parts-negative.spec.ts::API-PARTS-053` asserts `201` with `category === null`, and then cleans up the probe part (PATCH `active: false` → DELETE). The test title documents the surprise: "POST /api/part/ with name only actually succeeds".

## Evidence

- `curl -X POST http://inventree.localhost/api/part/ -H "Authorization: Token inv-..." -d '{"name":"probe-only"}'` → HTTP 201, body contains `"category":null`. Reproduced in the Phase 2 transcript.
- Playwright run of `API-PARTS-053` (original expect 400): failed with "Expected: 400, Received: 201".
