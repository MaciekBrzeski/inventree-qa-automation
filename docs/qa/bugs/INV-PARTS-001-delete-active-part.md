# INV-PARTS-001 — DELETE on active part returns 400 with unclear error

## Summary

`DELETE /api/part/{id}/` refuses to delete a Part while `active=true`, responding with HTTP 400 instead of 204. The agent-generated automated test case `API-PARTS-005 delete part` failed the first time it ran, because the manual test cases (generated by qa-gemma from the OpenAPI docs) did not capture this constraint — the OpenAPI schema describes `DELETE → 204` with no hint about the active-state precondition.

This is arguably a **documentation gap** rather than an API bug, but it has real QA consequences: every workflow that tries to clean up its own test parts via a direct DELETE will fail on the first run.

## Environment

- InvenTree: version `1.3.0`, apiVersion `477`, docker-compose stack (`inventree/docker-compose.yml`), Caddy proxy on port 80, internal inventree-server on 8000.
- Endpoint: `DELETE /api/part/{id}/`.
- Auth: Token auth (`Authorization: Token inv-...`), admin user.
- Reproduced from: `submission/automation/api/tests/parts-crud.spec.ts::API-PARTS-005`.

## Steps to reproduce

1. `POST /api/part/` with a minimal payload that omits `active` (defaults to `true`):

   ```http
   POST /api/part/
   Authorization: Token inv-<admin-token>
   Content-Type: application/json

   {
     "name": "QA-Part-xyz",
     "IPN": "QAP-xyz",
     "category": 1
   }
   ```

   Expect: `201 Created`, body contains `pk`. ✓ (observed)

2. Immediately attempt to delete the same part:

   ```http
   DELETE /api/part/<pk>/
   Authorization: Token inv-<admin-token>
   ```

   **Expected** (per `openapi-parts.filtered.json` → `paths./api/part/{id}/.delete.responses.204`): `204 No Content`.

   **Actual**: `400 Bad Request`.

## Workaround

Deactivate the part first, then delete:

```http
PATCH /api/part/<pk>/
Authorization: Token inv-<admin-token>
Content-Type: application/json

{"active": false}
```

…then `DELETE /api/part/<pk>/` → `204 No Content` ✓.

This is the pattern now used in `parts-crud.spec.ts::API-PARTS-005` and in the `afterAll` cleanup hook of the same file. See `submission/README.md` → "Agent fixes → Phase 2 API specs".

## Impact

- **Severity: low.** Core functionality works once the precondition is known. No data loss, no security risk, no regression.
- **Priority: P3.** Only affects teardown paths; humans deleting via the UI already hit the "deactivate first" button flow.
- **Consequence for QA automation**: every test suite that creates parts must either (a) seed them as `active: false`, (b) patch them inactive before teardown, or (c) rely on a database reset. Option (b) is adopted here.
- **Consequence for API consumers**: integrators writing automated part provisioning scripts will be surprised. The error message returned in the 400 body should at minimum say "cannot delete active part; set active=false first", and ideally the OpenAPI schema should document the 400 response with that reason.

## Proposed fixes (in order of preference)

1. **Best**: return a clear 400 body such as `{"detail": "Cannot delete active Part. Set active=false first."}` and document the 400 response in the OpenAPI schema for `DELETE /api/part/{id}/`.
2. **Alternative**: allow DELETE on active parts when the caller has the appropriate permission, behind a query param (`?force=true`) or header. This matches the "force" pattern used elsewhere in REST APIs.
3. **Minimum**: add a note in the InvenTree Parts documentation (`docs.inventree.org/en/stable/part/`) stating the deactivate-then-delete requirement.
